# Project notification inbox

## Problem and outcome

Slack messages, Linear updates, and email have become separate task lists. Blackbird needs one quiet, Inbox Zero intake where the user can understand each item, act on it, or hand it to an agent. Notifications remain separate from chats, with an explicit, durable connection when work becomes a chat.

## Scope

Linear agent-thread identity, bot avatars, hidden artificial session introductions and live working indication are defined in the linked [agent-thread indication spec](inbox-agent-thread-indicators.md).

Tracking exception for the reply-state change: proceed without a Linear issue, as explicitly requested on 2026-10-29.

Add an optional project notification inbox, source configuration, concise AI summaries, delegation, optional suggested resolutions, and memory of previous cases. All notification browsing happens in the left sidebar. Source access is read-only in this version: read, snooze, and resolution state belongs to Blackbird. Sending replies, archiving source messages, changing Linear issues, and synchronizing state back to sources are next steps, outside this scope. Suggestions and delegation do not grant additional source-write permissions.

## Required behavior

### Sidebar and notification contents

- Add top-level **Chats / Inbox** tabs within the left sidebar. Switching them preserves the current main-panel chat, draft, scroll position, and running agent. There is no middle-panel notification view.
- Reuse the existing Linear issue-view tab component and its sliding indicator, animation, and liquid-glass treatment. Reuse chat search, filters, row/menu conventions, and collapsed-section components wherever possible. Avoid a parallel sidebar design system.
- Show active notifications first. **Delegated**, **Snoozed**, and **Settled** use the existing chat section appearance and expansion behavior; their contents are collapsed by default and discoverable through their headers and filters. Only one of these collapsible sections can be open at a time: opening one through its header, keyboard navigation, or Show in Inbox closes the others. Active intake remains the main list. The open section’s heading sticks to the top of the scrolling list while its content is in view, using a full-width translucent liquid-glass sidebar tint with blur and saturation so the title stays readable over scrolling content. The glass surface extends through the sidebar’s horizontal content insets to both edges, leaving no side gaps; keep the label aligned with the list content. Keep the toggle borderless, with an understated underline for keyboard focus instead of a surrounding ring. Keep focused notification headers below this sticky heading.
- Each notification has its source app logo, actor/author, source location, and AI summary as its primary content. Show hour and minute for activity on the current local calendar day, a compact date for other days, and the full date and time on hover, honoring the client time format. Remove the separate one-sentence description and collapsed original-content preview. Summaries are one to five sentences, as short as possible; collapsed rows show a bounded preview. Opening a row reveals the full summary, optional suggested next steps, and original source content below it. While processing is pending or unavailable, show the source title and processing status; the original remains available on expansion.
- Group activity by source-native context where possible: a Slack thread, Linear issue, or email conversation. Preserve the exact triggering messages/comments and enough surrounding context to understand the request without another initial information-gathering step. Grouping must not discard individual notification details or invent cross-source identity.
- Clicking or arrow-focusing a notification expands it and smoothly collapses the previous item. Only one notification is open at a time. Focus controls expansion; ordinary Enter does not collapse the focused item.
- Settling the focused notification advances focus to and expands the next visible unsettled notification in rendered order. At the end, focus the previous remaining item; when none remain, focus the list. Advance only after a successful save and only if the user has not moved focus elsewhere while it was pending. The next item's automatic read does not replace settlement as the next Cmd+Z action.
- Raw content stays usable while AI processing is pending or unavailable. Summary failure must not hide the source item. Connection failures identify the affected source without blocking healthy sources or disguising stale content as current.

### Read status and lifecycle

Read/unread is independent of whether an item is active, delegated, snoozed, or settled. A chat link is also preserved across snooze and resolution.

- Clicking or arrow-focusing marks the notification read. Its read-state action and context menu allow **Mark as unread**. Doing so while it remains focused must stick; the same focus must not immediately mark it read again. Leaving and focusing it again marks it read.
- Delegating moves the item out of active intake into **Delegated**, visibly associated with its chat.
- Snoozing hides the item until the chosen time. Unsnooze or expiry restores the appropriate active/delegated placement, retaining the chat link. Reuse existing snooze choices and controls.
- Settling moves it to **Settled**. A visible **Un-settle** action restores the appropriate active/delegated placement. Settling does not delete source content, chat history, or the link.
- Settling the linked chat settles its notification; reopening that chat restores the notification to Delegated. A notification resurfaced by a later source reply must not be settled again merely because its linked chat is still settled. Notification settlement itself is not permission to erase a chat or its work.
- New activity in an already delegated source conversation retains the connection to its existing chat instead of creating a duplicate task. Whether that activity should start another agent turn is addressed under assumptions below.
- Persist notification state and links through restart and reconnect; connected clients must converge on the same project state.

### Reply updates

- Apply these rules to Mail through Superhuman, Slack replies, and Linear comment replies. Other Linear activity and automated-activity policy remain unchanged. Identify self through connected Slack/Linear user IDs and direct connected email addresses; exclude send-as aliases and display-name matching. Unknown authors must not be assumed to be self.
- A newly observed self-authored reply marks the existing notification read, preserving its placement, snooze, and chat link. Self-authored activity alone must not create a notification, reopen a settled item, or promote it as new work. Keep the reply as conversation context.
- A subsequent reply from someone else marks the same notification unread. If it is Settled, return it to active intake, retaining its identity, history, and linked chat. Do not create another notification or chat for the same source conversation. Other placements retain their existing behavior.
- Process new replies in source order, not fetch or page order. An incoming reply followed by a self reply in the same sync ends read; the reverse order ends unread. If the incoming reply reopens a settled item, the subsequent self reply marks it read without settling it again. Do not discard unseen incoming replies because the latest message is from self.
- Duplicate deliveries, retries, older history, and context hydration must not replay read/reopen transitions or undo a later manual read/settle decision. A self-only batch still advances a successful source checkpoint; a failed intake remains recoverable without skipping later replies. Preserve existing source selection, history limits, truncation notices, and project/connection boundaries.

### Two delegation actions

| Action                     | Icon                 | Behavior without a linked chat                                                                                                        |
| -------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Agent** — primary        | `bot`                | Create a linked chat and immediately start the configured agent using the project's editable default prompt and notification context. |
| **Agent chat** — secondary | `bot-message-square` | Create and open a linked chat with notification context, then wait for user input without starting an agent turn.                     |

Direct delegation can run while the user's current main-panel chat stays open. Agent chat intentionally opens the new chat. Both actions place the notification in Delegated once the link is established. If a chat is already linked, either action simply opens that same chat: no duplicate chat and no additional agent turn.

In the notification, both agent buttons open an existing linked chat and their tooltips make this clear; omit the redundant “Linked chat” text link. In the chat, the originating notification, source location, AI summary, expandable original content, and links back to the notification and original item appear in the existing **top-right Details bubble**. Do not add a competing notification panel in the main chat area.

The Inbox and the linked chat's Notification section show the same current conversation after source sync, including self replies, later incoming replies, relevant previews, and enabled AI summaries. Keep this current while the user stays in the chat with the Inbox closed, and after reopening or reconnecting a client. Both views use the same notification state and preserved chat link. Retain the existing source polling cadence; refreshing the panel alone is insufficient if intake or stored context is stale.

Repeated activation, retries, or concurrent clients must not create duplicate chats or turns. A failed chat creation leaves the notification actionable. If creation succeeds but agent startup fails, preserve the linked chat and expose the failure and a recovery path; do not present it as successfully running.

### Keyboard interaction and undo

These shortcuts apply when the inbox list owns focus, not while typing in search, a composer, an editor, or a terminal. Reuse the application's platform modifier convention outside macOS.

| Shortcut        | Action                                                                                                                      |
| --------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Up / Down       | Move notification focus; expand the new item and collapse the old one.                                                      |
| Cmd+Up / Down   | Jump to the current section's first / last notification; at that edge, move just one notification in the arrow's direction. |
| Cmd+Enter       | Direct Agent delegation; open the existing chat when already linked.                                                        |
| Cmd+Shift+Enter | Open Agent chat to compose; open the existing chat when already linked.                                                     |
| Cmd+Shift+H     | Snooze / unsnooze.                                                                                                          |
| Cmd+Shift+U     | Toggle read / unread.                                                                                                       |
| Cmd+Shift+O     | Open the focused notification's original source.                                                                            |
| Cmd+E           | Settle.                                                                                                                     |
| Cmd+Z           | Undo notification actions in order, including delegation.                                                                   |

For Cmd+Up / Down, a group means a sidebar section: active intake, Delegated, Snoozed, or Settled, rather than a source-native message thread. Within a section, jump to its first or last available notification. If already at that edge, handle the press exactly like an unmodified arrow: move only to the adjacent notification in rendered navigation order, entering the next section at its near edge without jumping through it. The next press can then jump to the far edge of that section. For example, Cmd+Down from the middle of Delegated moves to its last item; another Cmd+Down moves only to the first navigable item in the following section; a third moves to that section's last item. Cmd+Up mirrors this behavior. Both ordinary Up / Down and Cmd+Up / Down enter collapsed sections when crossing a boundary: expand the destination section, close any other open collapsible section, and focus its first item when moving down, or its last item when moving up. Never skip a nonempty section because it is collapsed. Skip sections with no matching notifications; at either end of the whole list, keep focus on the boundary item. Each destination receives keyboard focus, expands, and is smoothly scrolled into view when needed.

Holding Command shows mild shortcut hints over the focused row's action icons without changing layout. Command-number chat jumps do not navigate notifications or unexpectedly switch chats while the inbox list owns focus. Existing shortcuts retain their behavior outside that focus scope, including composer bindings that overlap these keys. Merely opening an existing chat is navigation, not a new delegation to undo.

Undo restores Blackbird notification state. After direct delegation has started the agent, Cmd+Z restores the notification to active intake and requests the agent to stop. Retain the linked chat and all completed work; cancellation does not roll back completed effects. The restored active notification keeps its chat link, so either delegation action subsequently opens that chat without creating another chat or starting another turn. A stop request must not be presented as a confirmed stop until acknowledged; expose a failed stop request with a recovery path. Marking an item unread through Undo must also survive the current focus.

### Initial history

Keep **Initial history** inside the expanded project Features → Inbox component, ahead of AI summary. One integer setting applies to Slack, Linear and Superhuman, defaults to 7, and accepts 0–30 inclusive. Zero starts collection at the server-recorded Inbox enable time, including sources connected later; restarts and sync overlap must not move that boundary backward. Re-enabling starts a new window. Changing the shared history value reapplies that window on the next sync. Preserve existing imported notifications. Remove per-integration history inputs; legacy per-source history fields remain wire-compatible but no longer control collection. Apply source-side date filters where supported and enforce the cutoff before ingestion. A relevant thread or issue can still include earlier messages as context for an in-window notification.

### AI summaries, suggested resolutions, and memory

- Summarize the message's substance and what the recipient needs to do, preserving the subject, requested deliverable and explicit deadline. Prefer one sentence; omit sender, application, read status and importance labels unless essential. When there is no request, summarize the actual update without inventing work. For example, a request for a PHP security report by EOD becomes “Send the PHP security report by EOD.” Keep the model and prompt editable. When AI summary is enabled, withhold a notification from Inbox lists/counts/search until summary generation succeeds or exhausts three total attempts. Retry failures after 5 and 10 seconds; each attempt times out after one minute. Persist attempts and retry deadlines so restarts do not reset the budget. After the third failure, deliver the notification with exactly “AI summary not available.” Never show “AI summary pending” or a summary retry/regeneration control. AI summary off keeps raw notifications immediately available.
- Parse Slack mrkdwn into safe readable formatting before display and summary context: labeled/ordinary links, people and group mentions, broadcast mentions, formatting and code. Resolve user display names with users:read and group handles with usergroups:read; keep readable IDs/embedded labels if an older connection lacks profile access. Use full native messages instead of abbreviated search hits, and retain text-bearing Block Kit/attachment content without fetching media. Keep the existing text content format and a readable plain-text body for older clients/model context, with optional formatted content for current clients. Omit formatted bodies from list previews and bounded model context. Repair cached formatting and enrichment without marking read messages unread or changing triage/chat links; invalidate affected summaries. Reauthorization reloads the selected shared history window to enrich retained messages.
- Convert Superhuman email HTML into readable plain text before display, summary generation and delegation. Preserve paragraphs, lists, useful links and decoded entities; exclude scripts, styles, hidden content and images, including tracking pixels. Do not execute HTML or fetch remote assets. Repair previously cached HTML without changing read status, triage state or chat links; invalidate summaries derived from that HTML so enabled processing can regenerate them. Open original remains the path to the source's rich email view. Display the email subject in bold above an eight-line body preview, with independent Read more/Show less only when it overflows. Omit the Original message introduction and redundant generated From/UTC timestamp envelope from the body; preserve greetings, body text, links and the normal source metadata bar.
- **AI summary** and **Agent Delegation** are independently disabled by default in project Features → Inbox. Enabling one expands its model and prompt controls. Each prompt input contains editable default instructions immediately; no separate custom-prompt switch exists. Blank input falls back to those defaults. Disabling a subgroup retains its model and prompt, hides its controls, and stops the corresponding capability: AI summary off skips preprocessing and hides generated text, Agent Delegation off hides/blocks direct runs. Compose-first Agent chat and navigation to an already-linked chat remain available. The environment enforces these opt-ins for RPC, MCP, background queue and keyboard paths. Changing a model or prompt must not rewrite raw source content.
- Optional **pre-resolution** researches suggested next steps after the summarized notification is first requested by a client. Use bounded, read-only project-file, project-chat, Inbox, and supported source-control-link tools. Persist researching, ready, checked-empty and unavailable outcomes independently of summary generation. Retry research up to three attempts with increasing delays; an explicit retry preserves the summary. Show no suggestion or unavailability beside the summary title, with a retry action for unavailability; researching uses a moving gradient bulb and rotating short phrases. Smoothly reveal or collapse a ready suggestion callout, respecting reduced motion. It may show a step-by-step process, suggested actions, or a drafted response. Its setting is disabled while AI summary is off, retaining the saved opt-in for re-enabling. Display suggestions in a subtle callout next to the summary, without an extra action button. Direct Agent uses the suggestion as the task alongside the project delegation instructions. Agent chat opens and focuses its composer with the suggestion prefilled, without sending it; preserve an existing user draft. Suggestions never automatically settle the notification.
- Inbox memory is optional and disabled by default. Explain it as building a database of recurring tasks and confirmed resolutions so patterns can improve suggestions for similar work. Ordinary notification/chat context remains available without it; this opt-in controls reuse of historical resolutions, not access to context. When enabled, processing and preprocessing look up similar previous notifications/cases and their confirmed outcomes within the same project to inform suggestions. When disabled, skip history retrieval and do not pass cross-notification precedents to processing. Disabling memory retains saved outcomes without using them for new processing; the confirmed-outcome editor is available only while memory is enabled. Memory covers the notification and its linked work, rather than only the summary text.
- Distinguish an observed resolution or response from an unconfirmed AI proposal. A settled state alone does not prove a successful answer. When no relevant precedent exists, suggestions must not imply there is one.

## Acceptance criteria

1. With Inbox off, the ordinary chat sidebar remains unchanged. Enable Inbox for project A and configure Slack; project B remains unconfigured even when it can reuse the same credentials. Enabling Inbox with Linear as a source does not turn on Linear view. Feature customizations and integration selections stay in their respective settings sections.
2. Switch Chats/Inbox while composing in an existing chat: the main panel and draft stay intact. Search and filter notifications with the reused controls. Delegated, Snoozed, and Settled use the chat section styling; opening one by click, arrows, or Show in Inbox closes the others. Scroll a long group and verify its heading remains visible at the top without obscuring a focused notification.
3. Move through Slack, Linear, and email notifications with arrows. Verify Cmd+Up / Down jumps within the current sidebar section, crosses its boundary by exactly one notification on the next press, then jumps within the newly entered section on the following press. Cover both directions, one-item sections, empty sections and the ends of the list. With and without Command, crossing into a collapsed nonempty section opens it and focuses its near-edge notification without skipping it or opening later sections; each newly focused item remains visible. Each has the required logo, source location, AI summary, and expandable original content. Only the focused item expands and becomes read. Mark it unread without moving focus; it remains unread until a later visit. Grouped comments retain their exact triggering context.
4. Direct delegation starts one agent with the project prompt; Agent chat starts no turn until the user submits. Repeated activation of either action opens the existing linked chat. Both sides expose the link, and the chat preview lives in its top-right Details bubble. Failed startup is visible and recoverable.
5. Snooze/unsnooze and settle/un-settle preserve read state and chat links. Settle and reopen the linked chat and observe the corresponding notification placement. Restart or reconnect a second client without losing these states or creating duplicate tasks.
6. Exercise every shortcut through keyboard focus and Command hints. No numbered chat jump fires from the inbox list, and overlapping composer/editor shortcuts still work elsewhere. Undo restores state, including an explicitly unread focused item. Undo direct delegation after the agent starts: the notification returns to active intake, a stop is requested, and the linked chat and completed work remain. Pending or failed cancellation is visible; later delegation opens the retained chat without starting another turn.
7. Verify AI summary, Agent Delegation and Inbox memory start off. Enable each subgroup and verify its model and prefilled prompt appear together, with no prompt toggle. Save distinct instructions/models, reload and verify project isolation. Disable and re-enable the groups to verify retained choices. With AI summary off, new notifications remain raw and no model call is made; direct-run requests fail while Agent Delegation is off, but compose-first and existing chat navigation work. Disable Inbox to hide all its details. Enable suggested resolutions and Inbox memory: confirmed same-project cases inform suggestions; absent/unconfirmed history is not fabricated. Raw content remains usable without AI, and processing does not write to sources.
8. Compare the implemented sidebar with the approved visual design at ordinary and resized sidebar widths, in both themes. Verify the metadata/summary/original hierarchy, summary shown only once, both agent icons on the left with Agent primary, quiet secondary actions on the right, current-state read/unread envelopes, section headers, and top-right Details integration. Shortcuts show without layout shift, and reduced motion removes the transition effects without changing behavior.
9. For Mail, Slack, and Linear comments, reply externally to an unread notification. After sync it is read with current context and unchanged identity, placement, and chat link. Self-only activity creates no item. Direct connected email addresses count as self; aliases and matching display names do not.
10. Reply yourself to a settled notification: it remains settled and becomes read. Receive another person's later reply: the same item returns active and unread with its existing chat link. Refreshing or reconnecting does not settle it again because the linked chat remains settled.
11. Sync an incoming reply followed by a self reply, then test the reverse order across pages. Final state follows source chronology without losing incoming context. Replay those replies after a manual Mark as unread or Settle: the manual state remains. A genuinely later incoming reply still marks unread and resurfaces a settled item. Process a self-only batch, then a later incoming reply; checkpoints and retries neither repeat transitions nor skip that reply.
12. Leave the linked chat's Notification section open with the Inbox closed while replies arrive. After sync, its context, previews, and enabled summary reflect the same conversation as the Inbox without a navigation cycle, duplicate item, or replacement chat. Verify the persisted result from another connected client and after reconnecting.

## Constraints and decisions

Reply updates must observe self replies without treating them as new work. Slack currently excludes them before ingestion; Superhuman ingests whole-thread changes; Linear notification intake knows the viewer ID but fetches actor names only. Verify reliable authorship and self-comment observation in the source APIs rather than assuming self notifications exist. Keep reads bounded and incremental. A context-only refresh must not be mistaken for new incoming activity.

Reuse [LinearIssueViewTabs](../../apps/web/src/components/linear/LinearIssueViews.tsx), [chat section headers](../../apps/web/src/components/ui/collapsible-section-header.tsx), and existing settings scope/inheritance controls. The current [Features page](../../apps/web/src/routes/settings.features.tsx) stores Linear view as a device preference; changing its scope is part of this feature, not an already available capability.

Keep state and source access in environment services with typed contracts and permission checks, available to local and remote clients and normal agent entry points. Do not put durable lifecycle rules solely in sidebar handlers. Fetch bounded previews and details without sending every source history to every client. Respect reduced motion and avoid continuously repainting animations. The sidebar design applies to web/desktop; mobile must preserve shared state and scope semantics, with its presentation decision noted below. Existing desktop-only Linear view restrictions remain.

Automatic summaries require an explicitly verified tool-free provider runner. Codex uses an isolated temporary directory, ignores user configuration and launch overrides, disables hooks and feature-owned tools, and supplies a model catalog with no shell, patch or experimental tools. Claude (without managed MCP) and Pi also meet this boundary; Cursor, Grok, OpenCode and Antigravity currently refuse automatic Inbox summaries before invoking their runner. Keep model/prompt selections editable; refusal uses the existing bounded retries and unavailable result. Read-only filesystem access alone is not sufficient isolation from external notification content.

Linear, Slack and Superhuman credential records use authenticated encryption with one environment-specific master key in the hosting OS credential store. Keep records separate and authenticate their identity; never store the master key beside them or fall back to plaintext when OS access fails. Convert existing plaintext JSON records atomically on first read. Upgrade the environment before using the new storage and do not run old and new servers against the same T3 home. Existing clients keep the same wire contracts. After conversion an old server cannot read credentials: prefer a forward fix, or disconnect/reconnect integrations when changing to an older storage implementation. Recovery requires both encrypted records and their OS key; if the key is lost, remove the affected connections through Disconnect and authorize them again. Do not silently replace the key while encrypted records remain. Existing Inbox triage/chat records and the legacy desktop credential document remain intact.

## Assumptions and open questions

- **Accepted source scope (2026-10-22):** support Slack DMs and personal/group mentions; display Saved/To-dos as unavailable until supported access exists. Superhuman's official Mail MCP documents split inboxes, labels, and thread filters; use its actual metadata, with authenticated access still to verify. Verify Linear notification retrieval and preserve its full notification-center semantics.
- **Proposed defaults, not separately approved:** the agent's next turn receives refreshed originating-notification context; source replies do not automatically start another turn, insert messages into the chat transcript, or change the chat's own settled state. Snoozed and delegated notification placement otherwise retains existing behavior. Overlapping source items in separately configured projects have independent state and memory; memory lookup does not cross project boundaries.
- **Linear view setup (2026-10-25):** users enable Linear view separately for each project. Remove the legacy device preference and its migration prompt; users can configure the feature again when needed. Upgrade the environment before clients enable Inbox. Older clients cannot use Inbox, and updated clients must report unavailable support on older environments. Rollback must retain new notification records for a later forward upgrade.
- **Accepted Linear connection architecture:** use one environment-owned OAuth connection per explicitly configured project for the existing Linear issue view and Inbox. Offer migration of the existing desktop connection without changing workspace settings or enabling either feature. Preserve the legacy encrypted credential document for recovery; updated clients use the environment connection after migration.
- **Accepted client scope (2026-10-22):** ship the approved web/desktop inbox first. Preserve shared state and scope compatibility with mobile; native mobile inbox UI is deferred.
